# Vibecode Audit and Governance Guide

## Goal

The Vibecode module is used to detect and govern signals that look like they were produced by generative tools, template scaffolds, or automated flows. It is not meant to replace human judgment, but to provide an auditable, configurable, and blockable pre-review signal.

## Core capabilities

- Keyword detection for `vibecode`, `vibe`, `prompt-driven`, and similar terms
- Source classification into `llm_generated`, `template_generated`, `handwritten`, and `unknown`
- Generation-behavior detection for `generated by / generated with / autogenerated / prompt-driven` patterns
- Trace analysis for `trace`, `workflow`, `pipeline`, or `prompt->model->patch` style evidence
- Intent and goal validation for `intent`, `goal`, `objective`, and `aim` declarations
- Dynamic-rule management via configuration, with support for `patterns`, `weight`, `risk`, `actions`, `category`, and `label`
- Hierarchical classification with `hierarchy`, `category`, `review_priority`, and `confirmations`
- Risk scoring that combines behavior, trace, intent, and dynamic rule evidence
- Policy-driven gate evaluation via configuration

## Output artifacts

After running:

```bash
python -m specomega vibecode "Generated by ChatGPT: def hello(): return 'hi'" --output-dir .specomega/reports
```

You will get:

- `vibecode_report.json` for structured programmatic consumption
- `vibecode_report.md` for human review
- `vibecode_report.html` for browser-based audit views
- `vibecode_report.csv` for spreadsheet-based summaries
- `vibecode_gate.txt` for review or governance gate decisions

## Configuration

The configuration file is [.specomega/vibecode_config.json](../.specomega/vibecode_config.json) and supports:

- `threshold` for whether a content should be flagged
- `rules` for mapping source types to risk and actions
- `rules.<name>.patterns` for dynamic rule matching over generation, tracing, or intent signals
- `rules.<name>.weight` for increasing the Vibecode score when a rule matches
- `policy.block_on` for deciding when the run should be blocked

Example:

```json
{
  "threshold": 1,
  "policy": {"block_on": "medium"},
  "rules": {
    "llm_generated": {"risk": "high", "actions": ["review"]},
    "template_generated": {"risk": "medium", "actions": ["inspect"]}
  }
}
```

## Recommended usage

- Use stricter `block_on` rules for critical code paths
- Use looser rules for docs and example directories
- Connect `vibecode_gate.txt` into CI or approval workflows to create a governance checkpoint
